
# Backend для маршрутизатора API

Высокооптимизированный сервер для расчёта и оптимизации маршрутов доставки с поддержкой продвинутых алгоритмов, учётом дорожной ситуации и выбором типа транспорта (автомобиль, велосипед, пешком).

## 🧠 Архитектура и алгоритмы

### Общая схема работы

```
Адреса / координаты → Геокодинг → Матрица расстояний → Оптимизация → Оптимальный маршрут
                                    ↓
                          Учёт пробок из БД (штрафы)
```

### Выбор типа транспорта

В системе запущены три отдельных OSRM-сервера:

| Тип транспорта | Контейнер | Порт | URL внутри Docker |
|----------------|-----------|------|-------------------|
| Автомобиль (driving) | `osrm-car` | 5000 | `http://osrm-car:5000` |
| Велосипед (cycling) | `osrm-bike` | 5001 | `http://osrm-bike:5001` |
| Пешком (walking) | `osrm-foot` | 5002 | `http://osrm-foot:5002` |

Параметр `transport` в запросе (`driving` / `cycling` / `walking`) определяет, какой сервер будет использоваться для построения маршрута.

### Базовые алгоритмы (всегда включены)

| Алгоритм | Сложность | Описание |
|----------|-----------|----------|
| **Nearest Neighbor** | O(n²) | Жадный алгоритм: на каждом шаге идём в ближайшую непосещённую точку |
| **2-opt** | O(n²) | Локальная оптимизация: убирает пересечения рёбер, «выпрямляет» маршрут |

### Продвинутые алгоритмы (опционально)

| Алгоритм | Сложность | Описание |
|----------|-----------|----------|
| **Or-opt** | O(n³) | Перемещает сегменты из 1–3 точек, улучшая локальную структуру маршрута |
| **Simulated Annealing** | O(n²·k) | Имитация отжига — позволяет выходить из локальных минимумов |

### Оптимизации производительности

- **Векторизованный Haversine** — расчёт матрицы расстояний в 50+ раз быстрее через NumPy
- **LRU-кэш OSRM** — повторные запросы к OSRM возвращаются из кэша (512 записей)
- **Оптимизированный 2-opt** — пересчитывается только изменённая часть маршрута

## 🚦 Учёт пробок и дорожных событий

### Как это работает

1. **Сбор данных** — парсер (или демо-функция) собирает информацию о пробках, ДТП и перекрытиях
2. **Хранение** — все события сохраняются в PostgreSQL с TTL 2 часа
3. **Штрафы** — при построении матрицы расстояний для точек, рядом с которыми есть пробка, веса всех рёбер умножаются на коэффициент (зависит от severity)
4. **Оптимизация** — алгоритм `Nearest Neighbor` видит эти точки как «дорогие» и откладывает их посещение на конец

### Влияние severity на штраф

| Уровень пробки (severity) | Штраф (penalty) | Эффект на маршрут |
|--------------------------|-----------------|-------------------|
| 1 (слабая) | ×1.2 | Может стать предпоследней |
| 3 (средняя) | ×1.6 | Смещается к концу |
| 5 (сильная) | ×2.0 | С высокой вероятностью — последняя |

| Метод | URL | Описание |

## 📡 Основные эндпоинты

| Метод | URL | Описание |
|-------|-----|----------|
| GET | `/health` | Проверка статуса сервера и доступности OSRM |

## 🐳 Запуск через Docker

Проект полностью контейнеризирован. Все сервисы (бэкенд, PostgreSQL, 3 OSRM-сервера) поднимаются одной командой.

```bash
# Запуск всех сервисов
docker-compose up -d

# Остановка
docker-compose down

# Пересборка с очисткой кэша
docker-compose build --no-cache

# Просмотр логов конкретного сервиса
docker logs osrm-car -f
docker logs osrm-bike -f
docker logs osrm-foot -f
```

## 🚀 Деплой на сервер

### Предварительные требования

- Установленный Docker и Docker Compose на сервере
- Доступ к репозиторию (Git)

### Шаг 1: Клонирование репозитория

```bash
git clone https://github.com/Argon573/Optimization-urban-delivery-routes.git
cd Optimization-urban-delivery-routes
```

### Шаг 2: Запуск всех сервисов

```bash
docker-compose up -d
```

Первый запуск займёт 20-30 минут — три OSRM-сервера будут обрабатывать карту параллельно.

### Шаг 3: Проверка статуса

```bash
# Проверка всех контейнеров
docker ps

# Проверка логов OSRM
docker logs osrm-car --tail 20
docker logs osrm-bike --tail 20
docker logs osrm-foot --tail 20
```

Когда все три сервера покажут `[info] Listening on port XXXX` — система готова.

### Шаг 4: Проверка API

```bash
curl http://localhost:8000/health
curl http://localhost:8000/road-events?lat=56.8380&lon=60.5975&radius_m=5000
```

### Важные замечания при деплое

1. **Имена сервисов внутри Docker:** код использует `osrm-car`, `osrm-bike`, `osrm-foot` — это корректно работает в Docker-сети без дополнительной настройки.
2. **Uvicorn host:** в `docker-compose.yml` команда должна содержать `--host 0.0.0.0`, чтобы контейнеры могли общаться.
3. **Файлы карты:** обработанные файлы сохранятся в папке `osrm-data/`. При повторных запусках переобработки не будет.
4. **База данных:** данные PostgreSQL сохраняются в папке `postgres-data/`.


## ⚠️ Важно

1. **Минимум 2 точки** для расчёта маршрута
2. **Максимум 50 точек** (для соблюдения таймаутов OSRM)
3. **Формат координат:** сначала `lat` (широта), потом `lon` (долгота)
4. Можно передавать не только координаты, но и адреса (`city`, `street`, `house`). Система выполнит геокодирование автоматически.
5. Если какой-то OSRM сервер недоступен — используется евклидово расстояние (формула гаверсинуса) с пометкой `matrix_source: "euclidean"`.

### Фиксированные start / end точки

Можно задать начальную (`start_point`) и конечную (`end_point`) точки. Маршрут будет построен с фиксированным стартом и финишем, а промежуточные точки оптимизируются между ними.

## 📊 Производительность

| Сценарий | Кол-во точек | Время (≈) |
|----------|--------------|-----------|
| Nearest Neighbor | 50 | < 10 мс |
| NN + 2-opt | 50 | < 50 мс |
| NN + 2-opt + Or-opt | 50 | < 200 мс |
| + Simulated Annealing | 50 | < 1 с |

*Основное время занимают сетевые запросы к OSRM. При использовании кэша повторные запросы выполняются за миллисекунды.*
